## 混杂变量：scheduler token budget（0817 新标注）

- `max_num_batched_tokens=16384`；C≥17 时 C×1024 prefill 超预算 → chunked prefill 分批 → AR 的 waiting 混入 token-budget 瞬时排队。与观测吻合：C=16 恰好 16×1024=16384 不触发、waiting=0；C=20 起 waiting=2→62 而 running 始终=C、kv 远未满。
- vLLM 0.26.0 官方说明：speculative decoding 下实际 `max_num_scheduled_tokens` 可能比 max_num_batched_tokens 更小（drafter 向 batch 加入额外 token slots）。
- **处置**：AR 高 C 段 waiting 不与 DFlash 直接对读；后续每点记录 resolved max_num_scheduled_tokens（AR/DFlash 都记）。
- DFlash 侧干净：prefill 9×1024=9,216 ≪ 16,384；verify ~9×16=144 tok/iter 也不触顶 → DFlash waiting 基本纯 KV admission。

## 四个数卡死任何简单模型

| | 满长口径(4096) | 实长口径(1280) | 实测 C_eff |
|---|---|---|---|
| AR | 61（源码） | 195（÷1280） | >96 未饱和 ✓ 两口径都不违反 |
| DFlash | 8.05（源码） | 25.75（÷1280，已废） | **9 ← 紧贴满长口径** |

- **推论 1**：AR 实测 >96 > 启动 61 → 运行时 admission 按实际长度，不做满长预留。C=96 kv=0.86 反解 ≈104MB/请求，介于 1280 朴素需求（~94MB）与满长 183MB 之间且靠近前者 ✓。
- **推论 2**：DFlash 实测 9 ≈ 8.05、远离 25.75 → 运行时预留接近满长最坏。kv=0.975 反解 ≈0.975×9.65GB÷9 ≈ **1.05GB/请求**，接近 4096 最坏的 1.2GB；而 1280 朴素需求仅 ~0.2-0.3GB → **放大 ~4-6x**。
- 同一 scheduler、同一 KVCacheManager，两种模式预留行为不对称 → DFlash 路径存在专属放大机制 = H1-H4。（反解数字依赖 kv_usage 口径假设，精确值以 ledger 为准）

## DFlash per-req 502 blocks 之谜（ledger 第一目标）

由启动日志反解：4039 blocks ÷ 8.05x ≈ **502 blocks ≈ 1.2GB/请求**（4096 满长）。但按 AR 同法朴素估算（mamba 48页×2.39MB + FA 8×256×64KB + drafter ≈ 0.28GB ≈ 117 blocks → 34.5x）与 8.05 不符，**缺口 ~4.3x 未解释**。需要 startup spec dump：各 spec 的 page_size_bytes / page_size_padded / block_size / SW window / num_speculative_blocks 精确值，逐项分解 502。
