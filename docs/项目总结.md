# LiteDrafter

LiteDrafter 研究资源受限 GPU 上的 speculative decoding serving。项目关注的不是单请求 decode 是否更快，而是：DFlash 的单请求加速能否在 vLLM continuous batching 中转化为真实吞吐，以及容量损失来自哪里。

当前重点是单卡 RTX 4090、vLLM 0.26.0、V2 Model Runner、Qwen3.5-4B Hybrid 和 DFlash drafter。

## 核心发现

Hybrid 模型的主要瓶颈是 Mamba/GDN speculative state，而不是 attention kernel 或 page 对齐。当前 DFlash KV layout 约包含 24 个 Mamba group、8 个 target FullAttention group、5 个 SlidingWindow group 和 1 个 drafter FullAttention group。

在 `n_spec=15` 时，每个请求约需要 426 blocks，其中约 384 个来自 Mamba，占 admission 需求约 93%。因此 speculative token 数增加会近似线性放大每请求容量成本。

## vLLM 动态 K 的容量盲区

vLLM 0.26.0 支持按当前 scheduler batch 选择 speculative token 数：

```json
{"num_speculative_tokens":15,"num_speculative_tokens_per_batch_size":[[1,4,15],[5,64,3]]}
```

每个三元组是 `[最小 batch, 最大 batch, K]`。上述配置表示当前 scheduler step 有 1~4 个 request 时使用 K=15，有 5~64 个 request 时使用 K=3。这里的 batch 是当前 scheduler step 选中的 request 数。

原始 Hybrid 路径中，动态表改变了 model runner 的计算宽度，但 Mamba speculative admission 仍按启动时最大值初始化，形成：

```text
实际计算：K=3
容量预留：K=15
```

Phase A 实测表明，高并发时只有前三个 speculative position 有效，但 running ceiling 仍约为固定 `n_spec=15` 的 9 个请求，吞吐约 462 tok/s。

## Admission patch

补丁把 scheduler 当前选择的有效 K 接入 Mamba speculative block 的 admission 和释放路径：

```text
当前 scheduler K -> 按当前 K 申请 blocks -> target 验证
-> accepted state 提交 -> rejected state 释放 -> 下一轮重新选择 K
```

只修改 `num_speculative_tokens_to_schedule` 会再次出现“省计算、不省容量”的假优化；真正修改必须同时影响 Mamba block accounting 和 release。

## Patch 后效果

固定 workload 约为输入 1024 tokens、输出 256 tokens：

| 配置 | C | 结果 |
|---|---:|---|
| patch 前动态 K | 16 | running 约 9，capacity waiting，约 462 tok/s |
| patch G2 | 16 | running=16，无 capacity waiting，约 699 tok/s |
| patch G2 | 32 | 稳态容量包络约 31 running，约 955 tok/s |

C=32 时 running 会因请求完成和新请求准入在约 27~31 之间锯齿；稳态 KV 使用率约 0.92~1.00。prefill 爬坡和最后 drain 不属于稳态容量。

## 复现实验

修改 `scripts/c_eff_scan.py` 中的模型和环境路径后运行：

```bash
python scripts/c_eff_scan.py --mode dflash --num-spec-tokens 7 --concurrencies 1,4,8,16,24,32
python scripts/c_eff_scan.py --mode dflash --num-spec-tokens 15 --spec-schedule '[[1,4,15],[5,64,3]]' --concurrencies 4,8,16
```

默认数据集是 `data/codecontests_qwen35_4b_1024_256.jsonl`。结果写入 `outputs/`，日志写入 `logs/`，默认不上传。

## 统计口径

- `C` 是客户端 closed-loop 并发度；`running` 和 `waiting` 是时变 gauge。
- `max_running` 和 `max_waiting` 是独立峰值，可能发生在不同阶段，不能直接相加。
- 容量结论使用 raw telemetry 的稳态窗口，排除 prefill 爬坡和 drain。
- server speculative counter 包含 settling 请求；客户端吞吐排除前 C 个完成请求。
- acceptance length 和吞吐不能证明输出正确性，需要 token-level 或 task-level 校验。

## 仓库结构

`scripts/` 是实验脚本，`data/` 是 metadata 和小型输入，`env/` 是环境快照，`docs/` 是归因文档，`results/` 是结果摘要。模型权重、密码、运行中的服务和远端绝对路径不属于仓库。

## 后续工作

继续验证 admission patch 在完成、拒绝 token、EOS、preemption 和 K 改变时的 state 提交与释放；之后评估 target/drafter 独立 physical KV layout，再做 Mamba state 压缩和 D-Cut。

## 前期归因工作：我们如何一步步找到瓶颈

### 1. 先冻结环境和实验协议

为了避免不同版本、模型和 workload 造成误判，我们先固定了单卡 RTX 4090、vLLM 0.26.0、PyTorch 2.11、CUDA 13.0、Qwen3.5-4B Hybrid 和对应 DFlash drafter。主 workload 固定为约 1024 输入 token、256 输出 token，并统一使用 streaming、closed-loop、固定随机种子和 settling 统计规则。

这一步的目的，是让后续变化只来自并发度、`n_spec` 或 admission patch，而不是环境漂移。

### 2. 做静态显存审计

我们分别测量了：

- 空进程显存；
- target 权重加载后显存；
- drafter 权重加载后显存；
- vLLM 可用 KV cache memory；
- GPU KV cache tokens；
- block size、KV group 数和每请求 block 需求。

我们最初考虑过继续优化 attention page 对齐，但静态账本显示 Hybrid 的主要容量成本来自 Mamba state，因此把优化重点转向 admission。

### 3. 做 FullAttention 与 Hybrid 对照

FullAttention 架构的容量损失主要来自 drafter 权重增加和额外 KV。Hybrid 架构则同时受到异构 KV spec、Mamba state 和 drafter cache 的影响。

通过对照，我们确认不能把 FullAttention 的优化结论直接套到 Hybrid：FullAttention 适合先优化权重/显存占用，Hybrid 必须先分析 recurrent state 和 KV grouping。

### 4. 追踪 vLLM KV grouping 源码

我们沿着 vLLM 的 KVCacheSpec、grouping、block pool、scheduler 和 model runner 路径检查了物理布局。

发现 Hybrid DFlash 中 drafter 只有一个 FullAttention layer，而统一 grouping 使用各类 spec 的最小 layer 数作为 group size，最终导致约 38 个物理 group：24 Mamba、8 target FullAttention、5 SlidingWindow、1 drafter FullAttention。

这个结果说明 Hybrid DFlash 的 KV token 容量大幅下降，首要原因是 recurrent Mamba/GDN state 必须为 speculative tokens 保留。group fragmentation 是额外的物理布局和管理损失，不能把它当作 KV token 下降的根因。

### 5. 做并发容量扫描

我们从低并发逐步增加 C，记录 running、waiting、KV utilization、capacity waiting、TTFT、TPOT 和整组吞吐。扫描发现 DFlash 单请求速度更好，但并发上升后很快进入 capacity waiting。

这证明问题不是单请求 kernel 变慢，而是每请求固定容量成本导致 scheduler 无法继续 admission。

### 6. 做 n_spec 反事实实验

为了验证 Mamba state 是否真的是因果瓶颈，我们只改变 `n_spec`：

- `n_spec=15`：约 9 个请求后 capacity waiting；
- `n_spec=7`：约 17 个请求后 capacity waiting；
- `n_spec=3`：约 31 个请求接近容量上限。

容量随 `n_spec` 变化，且变化与 Mamba speculative blocks 的线性关系一致。这比单点显存日志更强，因为它直接改变了导致容量成本的变量。

### 7. 建立 per-group ledger

我们在服务启动和运行时记录每种 KV spec 的 page size、group 数、blocks/request 和物理 bytes。ledger 显示 `n_spec=15` 时每请求约 426 blocks，其中 Mamba 约 384 blocks，占约 93%。

这一步把“感觉像 Mamba 占主要成本”变成了可审计的物理账本。

### 8. 验证 vLLM 动态 K 的实际行为

我们尝试使用 vLLM 已有的 `num_speculative_tokens_per_batch_size`，让低 batch 使用 K=15、高 batch 使用 K=3。

运行时发现高并发确实只计算前三个 speculative position，但原始 Hybrid admission 仍按启动最大 K=15 预留 Mamba state。于是出现“计算按 K=3、容量按 K=15”的容量盲区：高并发 running ceiling 仍约为 9，吞吐约 462 tok/s。

这次实验排除了“动态 K 本身没有生效”的解释，明确问题在计算路径和 admission 路径脱节。

### 9. 做 admission patch 验证

我们随后修改 admission 和 release 路径，使当前 scheduler 选择的有效 K 同时参与 Mamba speculative block accounting。验证结果：

- C=16：running 从约 9 提升到 16，capacity waiting 消失，吞吐约 699 tok/s；
- C=32：稳态容量包络约 31 running，吞吐约 955 tok/s；
- C=32 时 acceptance length 约 3.0 至 3.2，说明高并发 K=3 已真正生效；
- 无 preemption、无 request error、无 timeout。

### 10. 我们没有贸然做的尝试

我们暂时没有直接把 38 个 group 硬合并成 4 个，也没有先做 FP8 Mamba state 或 D-Cut。原因是：

- group 合并可能破坏 layer-to-block 映射，且不保证物理 bytes 按比例下降；
- state 低精度可能影响输出质量，必须先有严格 token-level 校验；
- D-Cut 主要减少 target verification 计算，不能直接消除 Mamba admission 成本。

因此工作顺序是先完成归因，再修复 admission，最后处理物理布局、state 压缩和计算优化。
