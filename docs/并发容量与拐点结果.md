# 阶段二 Step 2.A：Effective Concurrency Knee 扫描（2026-08-16）

> **做了什么：** 在 max_num_seqs=128（解除人为 32 上限）下，对 AR 和 DFlash 做 14 点 closed-loop 并发扫描（C=1..96），双通道采集客户端 streaming 指标 + 服务端 /metrics 指标。**结果：C_eff(DFlash)=9（running 钉死 9、kv 0.975 满、waiting=C-9 全 capacity），AR 到 96 仍未饱和（C_eff>96）。实测 9 与启动日志源码并发口径 8.05（4096 满长）几乎一致；÷1280 推算的 25.75 口径不成立、不作为 baseline（0817 修订，见 [[实验设计_C_eff归因_20260817]]）。**

## 实验目的

0812 三层实验发现 DFlash KV 容量 -86.8%（249,856 → 32,969 tokens，启动日志源码并发口径 8.05）。本实验测**动态服务容量拐点 C_eff**：running 何时停止增长、queue/TTFT 何时开始恶化。这是 group 碎片化修复（方向 B）的前置基线：修复后同协议重扫，C_eff 恢复量即修复收益的直接证据。

## 采集指标

**客户端（streaming per-request，settling 除外）：**
- TTFT p50/p95、TPOT p50/p95、E2E p50/p95
- output tokens 总量、output throughput (tok/s)、request throughput (req/s)

**服务端 /metrics 轮询（0.2s）gauge：**
- num_requests_running
- num_requests_waiting
- num_requests_waiting_by_reason{capacity, deferred}
- kv_cache_usage_perc

**服务端 counter / histogram（点首尾取差）：**
- Δnum_preemptions
- request_queue_time_seconds（**queue time 以服务端为准**）：count / mean / p50 / p95
- request_prefill_time_seconds：count / mean / p50 / p95
- request_decode_time_seconds：count / mean / p50 / p95

已验证 8 个指标全部存在于 vLLM 0.26.0（loggers.py:494/504/514/562/662/923/943/953）。

## C_eff 判定标准（knee）

```
C increasing
  → running requests 停止增长 (plateau)
  → waiting requests > 0
  → queue time 突然上升
  → TTFT p95 突然上升
同时成立的第一个 C = C_eff
```

timeout / preemption 仅作为佐证记录，不参与判定。

**DFlash 判定：C_eff = 9（plateau 值），knee 在 C=12 首次显现。** 四条件齐活：

1. **running plateau**：C≥12 后 max_run 钉死 9.0，不再随 C 增长
2. **waiting 线性堆积**：max_wait = C−9 精确成立（3→87），**100% capacity 标签**（deferred 恒 0）
3. **queue time 跳变**：q_p95 从 C=8 的 0.28s → C=12 的 1.84s（6.6x）→ C=96 的 39.4s
4. **TTFT p95 跳变**：0.26s → 1.98s（7.6x）→ 32.77s（每 +1 并发 ≈ +0.36s 线性恶化）
5. （佐证）吞吐平台：C≥12 后 605-659 tok/s 不再增长；kv_cache_usage 0.975 满

### 核心对比

| 指标 | AR | DFlash | 差距 |
|---|---|---|---|
| C_eff | >96（∈(96,128]） | **9** | **≥10.7x** |
| 饱和吞吐 | >1300 tok/s（仍爬升） | ~620 tok/s（平台） | ≥2.1x |
| C=96 时 TTFT p95 | 3.59s | 32.77s | 9.1x |
| preemption | 0 | 0 | vLLM 0.26 用 admission control 停止接纳，而非 preempt |

**吞吐交叉点**：DFlash/AR 吞吐比 C=1:3.1x → C=8:2.8x → C=12:2.2x → C=24:1.26x → **C=32:0.95x（反超）** → C=96:0.47x。与 0812 burst 协议的交叉区间（16-32）一致。

### 动态实测 vs 静态口径（0817 修订）

| 口径 | AR | DFlash | 状态 |
|---|---|---|---|
| 启动日志源码并发（4096 满长最坏） | 61.00 | 8.05 | 事实 |
| ÷1280 workload 推算 | 195 | 25.75 | **口径不成立，不作为 baseline**（假设每请求 KV 需求随长度线性缩，忽略 mamba 常数 state 与页对齐 block） |
| 动态实测 C_eff | >96（∈(96,128]） | 9 | 事实 |

- "25.75→9 = 2.86x 碎片化损失"表述**已删除**——分子口径不成立，该比较无意义（0817 裁定）。
- DFlash 实测 9 ≈ 启动口径 8.05（差 12%）：目前只是观测，机制未证明。由 kv=0.975 反解运行时每请求预留 ≈ 0.975×9.65GB÷9 ≈ 1.05GB，接近 4096 满长最坏的 1.2GB——即 DFlash 运行时预留接近满长最坏；而 AR 按实际长度缩放（C=96 时 kv 仅 0.86，反解 ≈104MB/请求 vs 满长 183MB）。预留不对称的机制 = H1-H4 假设清单（[[实验设计_C_eff归因_20260817]]）。
- ~~"绑定约束是页粒度分配"~~ 降级为假设：FA 页填充（H2）与 mamba 常数 state（H4）在字节/块两种口径下结论相反，谁先饱和未证明，待 per-group ledger 裁决。kv_usage 在 9 个请求（11,520 tok，token 容量的 35%）时报 97.5% 满仍是关键观测。页表对比（0812 L3 数据）：

|              | AR                     | DFlash                             |
| ------------ | ---------------------- | ---------------------------------- |
| groups       | 4（8层/组）                | 38（**1层/组**）                       |
| uniform page | 2.15 MB                | 2.39 MB（+11%）                      |
| 组成           | 3×Mamba(8层) + 1×FA(8层) | 24×Mamba(1层) + 9×FA(1层) + 5×SW(1层) |

**开放问题（per-group ledger，E3）**：plateau 时逐组输出 spec type / total / allocated / free blocks / page size / 每请求 block 增量，并对 admission 失败路径打点——指认"C=10 的第 10 个请求被哪个组挡住"。旧版"页对齐填充使 FA 组真实页消耗远超 token 口径"仅为假设 H2，未证明。

## 设计决策记录

1. **closed-loop**：稳态容量视角，knee 信号干净（vLLM benchmark_serving 标准语义）
2. **streaming + ignore_eos=True**：greedy 提前 EOS 会让实际 KV 占用 < 1280 tok/req，高并发点 KV 压力变小、knee 漂移。固定输出长度 = 每请求 KV 预算恒定。⚠️ 与 0812 不完全一致，跑前需确认
3. **queue time 以服务端 histogram 为准**：客户端无法区分排队与 prefill
4. **settling = 前 C 个 completion**（按完成序而非提交序）：吸收冷启动效应
5. **server histogram 含 settling 请求**（服务端无法区分），客户端统计已排除——口径差异已记录
6. **wait_ready 用 any()**：复用 0812 踩坑修复

## 踩坑记录

1. **`vllm:num_preemptions` 首次 preemption 前不出现在 /metrics**（loggers.py:1191 仅在 num_preempted_reqs>0 时 .inc()，Prometheus counter family 惰性注册）。初版自检把它当必需 gauge 导致 smoke 误报 FATAL。修复：自检只要求 running/waiting/kv_usage；preemption delta 逻辑本身不受影响（缺席=0，出现=累计值，首尾差正确）。
2. **histogram 低端分辨率粗**：vLLM request_latency_buckets 从 0.3s 起步（[0.3,0.5,0.8,1.0,1.5,2.0,2.5,5,10,...]）。queue time 很小时分位数有量化伪影（smoke: queue mean=16µs 但 p50=0.15s）。knee 判定用秒级区间的 p50/p95（1s-120s 段桶距 ≤2x，够用），低并发点的 queue 分位数忽略、看 mean。
3. **AR C=1 是健康慢点**：256 条 × ~9s ≈ 38min > 默认 point_timeout=1800s，正式跑提到 3600s，防止慢点被误标 TIMEOUT。
4. **ssh 单引号块内 heredoc 的 python f-string 引号会被转义破坏**（SyntaxError: unexpected character after line continuation character）。解决：python 脚本写本地文件，用 `ssh host 'python -' < localfile.py` 经 stdin 传入。
5. **L3 json 的 num_blocks 两组口径不一致**（AR=676 vs DFlash=4039）：DFlash 4039×2.39MB≈8.9GB 与 L1 KV 内存 8.85GiB 吻合（total pages），AR 676×2.15MB≈1.43GB 与 10.82GiB 不符（疑为每组页数）。跨模式对比 num_blocks 时以 KV 内存为准，不要直接比块数。→ **0817 已解**：676 是池总 group-blocks（每 block = 8 层 × 2.15MB ≈ 17.2MB），676×17.2MB ≈ 11.6GB = 10.82GiB ✓，见 [[三层容量实验_Qwen3.5-4B_20260812]] L3.5 修正版手算；DFlash 4039×2.39MB ≈ 9.65GB ≈ 8.85GiB ✓ 同口径，谜底 = num_blocks 单位是"group-block"而非裸页。
